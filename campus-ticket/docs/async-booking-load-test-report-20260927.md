# 异步报名并发测试报告（2026-09-27）

> 历史基线：本报告对应当时的定时投递方案，不代表当前立即投递、限流及自动候补完整版本。后续对比见 [立即投递报告](async-booking-immediate-load-report-20260927.md)，复跑口径见 [测试说明](testing.md)。

运行标识：`e203c33ba477`。测试通过，JUnit 1 个测试方法包含 5 个阶段，失败 0、错误 0；测试耗时 106.1 秒（包含准备、校验和清理），Maven 总耗时 2 分 57 秒。

## 测试方式

- 单个 Spring Boot 应用，启用 async 配置，随机 HTTP 端口；使用真实 MySQL、Redis、Kafka，经过登录鉴权、报名 HTTP 接口、Redis Lua、定时投递、Kafka 消费、数据库事务和 Redis 状态更新。
- 测试客户端与应用在同一 JVM，数据库在本机，Redis/Kafka 在虚拟机。客户端线程数代表同时发起请求的并发数，不能视为独立压测机测出的服务容量。
- 使用独立的 200 个学生、1 个管理员、5 个活动，以及独立 Kafka 主题和消费组。登录和创建活动不计入报名请求延迟。
- 为保护已有业务数据，测试禁用自动注册的定时任务，使用原任务类实例和测试调度器；仅将发现活动和恢复任务的查询范围限制为本次测试数据，其余数据库操作使用真实实现。
- 投递固定间隔 1000ms，每轮每个活动最多 10 条，恢复固定间隔 5000ms；保留当前生产批量与间隔，测试调度器首次立即运行。各阶段等待处理完成后才进入下一阶段。
- 最后一阶段使用同一批 200 个账号连续发送 5 轮，共 1000 个请求，验证重复报名拦截。它并不等同于 1000 个不同用户成功受理的积压测试。

HTTP 延迟从每个客户端请求发出前计时，包含本机 HTTP 通信及服务处理；P95/P99 包含正常业务拒绝，表示 95%/99% 的请求在该时间内完成。整批耗时从本阶段开始发请求计时，直到数据库全部进入终态且 pending 清空，不是每条订单的处理延迟分位数。

含预热共 1370 次报名请求：395 次受理并成功落库，175 次名额不足，800 次重复报名。所有阶段均满足：

- 非预期 HTTP 响应或传输错误为 0。
- 成功订单数与有效报名数均等于初始名额，没有超卖或重复有效报名。
- 数据库与 Redis 剩余名额最终均为 0；pending 最终均为 0。
- Redis 中每条受理记录最终均为 SUCCEEDED，数据库 FAILED 订单为 0。
- 同一订单重复 SUCCEEDED 日志为 0，测试死信主题消息数为 0。

采样观察到的 pending 最大值为 200，随后排空。客户端与服务端合计的 JVM 堆采样峰值约 120.76MiB，线程采样峰值 529；不能将这些指标当成应用独立资源占用或实际瞬时最大值。

## 发现的处理速度限制

报名受理与异步落库的速度差异明显：200 个有效申请的整批处理耗时约 39 秒，观察到约 5 条/秒的完成速度。

结合 BookingDispatchJob 的实现判断，主要限制来自定时投递：每次每活动最多领取 10 条；游标扫描到末尾后，还有一次空结果轮询用于重置游标。因此，本次少量活动条件下，同一活动通常约两秒获得一轮投递机会。这是对代码和测量结果的分析，不是通过独立性能剖析得出的 Kafka/数据库吞吐上限。

后续优先改进调度扫描与投递批量，再扩大有效申请数量测试。当前申请还有约两分钟有效期，更大的持续积压可能触发过期失败，本次最大 200 条积压在期限内排空，尚未覆盖该边界。

## 结论和范围

当前实现通过了本机单实例最高 200 并发的短时突发与重复报名测试，在本次范围内未发现一致性异常。不能据此宣称支持持续数千 QPS、千人同时成功报名或生产级高可用。

本次没有覆盖长时间持续负载、多应用实例共同消费、多个热门活动同时争抢，以及负载中杀进程、断开 Redis/Kafka/MySQL 等故障。取消报名恢复和 Kafka 重复消息处理见前一次功能测试报告，本次没有重新进行这些故障场景。
