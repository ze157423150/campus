# 功能边界与待办

以下依据当前代码整理，区分已有机制与尚未完整覆盖的场景。

## 优先补齐

1. **管理员取消活动的异步一致性。** ActivityService.cancelActivity 更新活动和 registration，并发布缓存失效事件；尚未完整批量同步对应 booking_order 的终态、redis_dirty 及 Redis 准入状态。个人订单取消已有候补交接流程，不能据此推断“取消整个活动”也已完成相同闭环。
2. **跨实例 L1 主动失效。** 当前其他实例依靠短 TTL 更新，可能短暂返回旧资料、旧空值或旧剩余数。失效版本防止旧重建覆盖，不替代广播。
3. **Redis 丢失后的重建与对账。** 已实现订单和任务补偿扫描，尚非完整的 Redis 整库恢复、库存全量核对及自动修复工具。

## 业务与运行边界

- 满额自动候补已实现，但普通报名与有效候补之间的所有竞争并非统一入口互斥；OFFER 会检查占用并安全跳过已有占用用户。不能声称所有路径都保证严格的候补优先权。
- 普通报名超时失败的库存回补与用户取消产生的候补名额不是同一条路径，不能把所有释放都描述为必定经过 FIFO 候补。
- 普通申请仍有处理期限，超过期限可能失败，不是永不超时、无限保证最终成功投递。
- Kafka 重复交付由业务幂等处理；不是跨 Redis、Kafka、MySQL 的 exactly-once 事务。死信和永久错误仍需观测与处理。
- 站内通知需要客户端查询；未实现短信、邮件、WebSocket 推送和前端界面。
- 场馆只提供资料及缓存查询，未关联活动档期，也没有场地冲突预订。
- 注册不验证真实学号归属，未对接校园统一身份认证；限流不等于完整反作弊系统。
- IP 限流按 remoteAddr；代理部署前需规划可信代理解析，不能直接信任任意 X-Forwarded-For。
- requests 历史终态、订单日志、通知和任务尚需统一归档与保留策略。
- 当前开发 Kafka 为单节点、单副本，测试结果不代表高可用部署；未进行完整 Redis Cluster 多键脚本兼容验证。

## 简历表述建议

可以写“基于 Redis Lua 原子预占、Kafka 异步消费和业务幂等，结合同步任务与定时补偿处理重复投递及部分中断场景”；可以写“实现候补限时确认、超时递补与公开库存回流”。

避免未经证据支持的“绝对不丢消息”“强一致多级缓存”“所有故障自动恢复”“生产级百万并发”。性能数字必须附测试条件，明确是 HTTP 接口耗时还是整批异步完成耗时。
